# Desktop dry-ink input and render-before-commit safety

## Goal and scope
The user rejected monotonous marks, not just missing UI switches. The repository already has a directional, pressure-dependent dry-ink renderer, but the desktop pointer path only used the old brush compiler. This change makes that existing renderer usable through actual desktop input; it does not introduce a generated image, texture overlay across the picture, or claim faithful artist-level reconstruction.

## Implementation
- Explicit dry-ink mode, width <=128 native pixels, <=4096 input points. Fixed hard edge is disclosed and hardness UI disabled. Eraser remains the old eraser engine. Mode, UUID, color, opacity, width and taper freeze at gesture start.
- Preview and release compile with the same UUID, persisted seed and source snapshot. Dry-ink helper rebases time once; synthetic tablet pressure/time are preserved, mouse taper remains optional. Over-limit input cancels the entire stroke, never silently truncates or switches to a different brush.
- A valid command is not enough: the renderer has an independent per-tile work budget. On release, a temporary document is rendered off the GUI thread before any paint command is committed. Busy blocks save/open/edit/replay/export and other workflow starts. Esc, explicit cancel, mode change or focus loss cancels the pending stroke.
- Completion uses a single mutex/generation-protected mailbox, moved event storage and a pre-existing GUI timer. No geometry copy or queued callback allocation is required on worker completion. Cancellation clears the mailbox under the generation lock; stale work cannot enter a new gesture. Before commit, document ID/revision/canvas generation are checked again.
- Render failure leaves the committed document unchanged and shows an error. Cancellation explicitly says this stroke was not written. The final committed frame is rendered again by the normal document path; large-canvas release may therefore take noticeable time despite a responsive event loop. No fluidity promise, no total process-RSS bound or exhaustive allocator-failure injection claim.

## Acceptance and review
Actual Qt input tests cover dry preview/commit pixel equality, deterministic event/seed save-reopen, Undo, pending save/edit/export/replay guards, cancellation, >4096-point whole-gesture cancellation, and a compile-valid complex retrace that hits render work limits without entering the document. Synthetic tablet pressure and relative timing survive untouched. Actual QML mode switch and disabled hardness control are exercised. Existing core B13 tests cover dry pressure, tile seam, replay and cancellation; Windows/physical pen are not tested.
Initial integration passed, then the mailbox/pressure revision passed three consecutive Qt/QML runs: 17.15 / 18.06 / 16.88 s. A subsequent extended input-limit pass took 16.83 s; final cancellation-notice/visual-diagnostic follow-through passed in 18.81 s. The complete rebuilt Release suite then passed 103/103 in 80.47 s. The first full attempt selected an incomplete toolchain Python and failed 22 missing PIL/yaml imports; configuration was corrected to the existing verified Python and the entire suite rerun, not waived. Independent review found and resolved worker completion allocation and worker-probe busy gaps; no unresolved blocking issue was reported in the mailbox review.

## Honest limitations
A dry brush is not a finished artwork. Texture recipe remains fixed; natural interpretation, careful lettering, source shape accuracy, original colors and nuanced finishing still require work. Existing strict lineart-fill stacks do not accept arbitrary hand-painted layer combinations; this is not a claim that every mixed drawing/fill workflow now works. Only synthetic diagnostic strokes were made in acceptance, not a new cover or comic. Private technical proof images are not part of this source upload. Keep stage reports and distinguish original/reference/processed/test/generated provenance.
